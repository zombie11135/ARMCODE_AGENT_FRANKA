4. 项目架构与策略后端
默认 policy_backend 仍为 template，不是 hybrid。
--policy_backend template：原任务图/动作模板基线。
--policy_backend cap：LLM 生成 Python；允许函数、有限循环、条件；AST 解释器调用技能。
--policy_backend hybrid：任务图组织有序 grasp/place 子任务，每个子任务生成代码，反馈驱动局部修复。
定位是借鉴 InstructFlow 任务图 + 任务级 CaP，不是完整复现 CaP-X/原论文所有控制能力。
当前代码接口只有 observe(target)、pick_place(target, container)。没有自由 Python/任意机器人坐标控制。
具体遮挡清障与重观测仍由技能内部恢复模块负责，不是 LLM 显式生成完整清障代码。
observe 的成功可能仅表示取得了可用场景，不能把 ensure_visible() 的名字当成身份已确认。
目标身份与几何仍在受控抓取入口再次检查。
主要代码：
  agents/simple_agent_system.py、agents/simple_execution_runtime.py
  agents/cap_code_generator.py、agents/cap_execution.py、agents/hybrid_execution.py
  runtime/cap_policy.py、runtime/task_state.py
参考 docs/cap_and_gentle_place_20261105.txt、docs/hybrid_occlusion_20261105.txt。

5. 已有流水线——继续工作前先读这些
A. 首帧感知与容器预观察重叠
  runtime/task_perception_pipeline.py：TaskPerceptionPipeline。
  主线程先冻结图像，单后台线程分析已有首帧、识别/建图，并在满足条件时预计算抓取候选。
  前台同时进行容器预观察；回到源观测位后等待结果并发布。
  后台 context 不持有 camera/arm/gripper，不负责硬件动作或占用缓冲位。
  publish 检查观测 epoch、任务绑定和捕获位姿；场景已改变或视角不符就丢弃结果。
  候选预计算需要 transforms 等条件，并非每次自动生效；实际是否预计算/命中必须查看报告。
  --disable_perception_pipeline 可作串行对照。
B. 下一子任务代码预生成
  agents/hybrid_execution.py：单后台线程，在执行当前子任务时预生成下一个子任务代码。
  代码绑定图 revision；修复图后废弃旧 future，生成当前节点新版本；完成前缀不重放。
  --disable_policy_pipeline 可作串行对照，仅影响 hybrid 代码预生成。
  单个 grasp/place 对没有下一子任务，不能用它评估代码预生成收益。
  future.cancel() 不能中止已运行的 LLM HTTP 请求；退出时 shutdown(wait=True) 可能等待完成。
  这是可检查的调度开销点，不是已经证明的瓶颈。
C. 已有资源与缓存
  runtime/perception_pipeline.py：GPU/OCR 资源序列化、有界工作队列。
  services/sam3_model_pool.py：共享冻结 SAM3 权重；每图/提示的 processor 状态独立。
  runtime/observation_memory.py、skill_lib/actions/observation_cache.py：场景/观测版本与位姿绑定。
  不要绕过现有版本检查，跨搬运复用旧图、旧抓取候选或轨迹。
D. 计时
  runtime/timing.py；文档 docs/task_timing.txt。
  task_timing.json：duration_s 是入口总墙钟；spans 有 start_s/duration_s/parent_id/background/线程等。
  GPU/OCR 锁等待也有记录；嵌套与并行 span 不可简单相加。
  TaskPerceptionPipeline 记录 analysis_s、candidate_prefetch_s、join_wait_s、候选缓存状态等。
  hybrid_trace.json 记录 prefetch_started/used/failed/invalidated；task_state.json 记录状态和预算。
  move 耗时包含通信、规划和执行，不是纯运动时长。
  预览窗口等待、人工故障处理也可能进入总耗时；实验需控制这些条件。
目前尚无同条件串行/流水线的真实端到端加速结论，不要将单元测试通过当成吞吐提升。

10. 下一会话建议执行顺序：以流水线为主
第一步：确认活动 SSD 仓库，读取本交接与 docs/hybrid_occlusion_20261105.txt、docs/task_timing.txt。
第二步：用至少两个 grasp/place 子任务建立串行、感知重叠、代码预生成、二者同时开启的对照。
  固定输入场景/模型/策略后端/采样设置和输出目录；将冷启动与热启动分开，不能比较不同任务。
  no_run_executor 仅能检查代码生成，无法测量运动与计算的重叠。
  先用模拟执行验证调度正确性，再在实际授权和现场条件下做真机时间线。
第三步：以总墙钟、join wait、锁等待、预生成命中/失效/浪费时间、成功率和重试数找瓶颈。
  用 spans 的时间区间检查重叠，不把重叠阶段相加，不以扩大预算、改变动作来冒充加速。
第四步：减少重复感知；以同帧 RGB-D/哈希和场景版本复用分割结果，保持处理器线程状态隔离。
第五步：将 InstaOrder 常驻后端接到在线同帧感知结果，输出正式边和待验证候选，再进入恢复快照。
  不重复运行 SAM；不让后台线程直接修改机器人状态；前台版本校验后发布。
  预计算对象若与 LLM 最终选择的遮挡物不同，应测量浪费，不能直接复用错误节点候选。
第六步：优化任务相关的探索收益；区分可见区域数量与任务信息，暂不打开不稳定碎片合并。
第七步：有当前标定/位姿、可行抓取和空闲缓冲位时做真实搬运→重观测，评估信息变化。
不要同时大改调度、感知算法、策略接口和执行顺序，否则无法解释性能提升来源。
